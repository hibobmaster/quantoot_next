# Accepted navigation stability design

The user needs stable Profile category transitions and Settings children with one title and one standard back action. Candidate A's coordinated header and single lazy body is the accepted base. The independent gpt-6-luna judge and root both score A 4/5 and B 4/5 against the five-item rubric. A loses the bounded-design point because its motion and cache coordination need careful implementation. B loses the useful-reading point because its conservative footer can produce a blank end viewport. Native feasibility remains a gate, not an inferred pass.

Both completed packages were read end to end. Candidate B proves that a one-list body floor can make every leading offset attainable. Its `max(0,V-n*48dp)` footer ignores the existing 88dp padding and actual tall-card height. With one post, the footer and padding can exceed one viewport. Subtracting padding prevents part of that overrun but retains a large artificial tail for sparse tall posts. The root rejects that visible tradeoff for this client's reading experience. The accepted controller keeps header travel independent of body size without that tail.

## Contract and synthesis

Use candidate A's naturally measured header, pinned zero-padding category row, and one lazy body. One parent scroll controller routes motion through header and body. There is no capped header or second independent vertical list. Empty and loading bodies can have zero scroll range while the header still travels naturally. After full collapse, posts use the viewport below the category row. All actual pagination and accessibility visibility calculations must respect the outer clip.

Apply two cross-judge grafts. First, selection and callbacks use a typed Profile selection interface. The final `ProfileTimeline` header slot contains profile fields and actions only, excluding tabs and Activity filters. `ProfileTimeline` renders a private `ProfileCategoryRow(selection,onSelect)` with the typed state and callback. This resolves the candidate's ambiguous zero-argument header without exposing selection to a field-only header caller. Second, drop the passive `ProfilePresentations` registry and any promise to retain the chosen category across child routes. Keep the existing route lifetime, which reconstructs Profile on Posts and restores that source's cache position. No AppShell registry/pruning API is added.

Category and Activity-filter selection retain the current header collapse and start the selected body at its beginning. An incoming source cache supplies projected rows and cursor, but must not replace that geometry. Only the selected source is active. Initial creation and child-route return use the existing source snapshot with explicit conversion from old leading pixels to header/body presentation. Status index and offset remain status coordinates. About has no pager or status cache.

Keep candidate A's snapshot identity fallback, no-footer-pixels rule, activation epochs, readiness and idempotent close behavior. Graft B's explicit distinction between safe cached position and deferred-arrival state: a footer after real statuses is reading older even when its safe snapshot is the last status at offset zero; an empty footer is not reading older. The viewport contract must expose those decisions separately. Do not derive deferral from a clamped footer snapshot alone.

Candidate A's immediate bounded memory checkpoint and single ordered writer remain behind FeedCache at the existing UiContext account lifetime. There are separate typed Status and Notification sessions, no serializer casts and no second row/cursor owner. Source disposal publishes a final ready snapshot before detaching and cannot publish through a newer attachment. Reads prefer a newer memory snapshot over a disk read that finished late. Ordinary disk writes retain a 400ms debounce. Account/process teardown remains best effort. This is not a promise of cross-process storage transactions.

For Settings, use one public `SettingsSection` enum with canonical title keys and account requirements. Replace object Screen.Settings with `Screen.Settings(section:SettingsSection?=null)`. Null means index. AppShell derives the localized title and content from that route. All callers migrate in the same unit. Normalize direct child navigation to include the index below it, replace a sibling child rather than stacking another, and retain existing Thread navigation behavior. Root and child standard back use ui.requestBack. The redundant Settings toolbar action is hidden on Settings routes. Account-only direct guest routes use the existing login prompt. Keep existing data/write handlers and composer interception unchanged. Remove the inner Settings return label and redundant Licenses/policy page headings, retaining policy content and server identity/tabs.

## Implementation units and ownership

Unit 1 is a native Profile motion prototype before feed wiring. Its isolated worktree adds the reusable controller/layout and pure geometry tests. Temporary probe wiring may replace Profile only in that worktree and must be clearly marked, recorded and removed before integration. It uses fixed header and empty/short/tall body cases to test actual UIKit/Compose motion, source-like body replacement, clipping, fling, reverse motion, refresh ordering and accessibility scrolling/bring-into-view. Prototype results are not live-feed acceptance.

Unit 2 implements typed Settings routes in a separate worktree. It owns Foundation.kt's Screen/navigateTo changes, Settings.kt, and the Settings branches/actions in QuanTootApp.kt, plus focused navigation tests. It must not change Profile, feed/cache or Home selection code. Root merges units sequentially. If the Profile integration needs UiContext cache fields, those changes are limited to the UiContext class and are reconciled with Unit 2's disjoint sections.

After the prototype is accepted, integrate the selected Profile controller with the existing status pager lifecycle and cache adapter. Profile owns Accounts.kt's profile header/body migration, new Profile controller files, Feeds.kt adapter extraction, FeedCache.kt checkpoint behavior and UiContext typed cache sessions. No Home route lifetime or status-projection ownership changes. Delete the old per-category Profile feed-leading path and independent About list in the same integration.

The reusable cache and pager adapter extraction may proceed in an isolated unit while root runs the native prototype, but it must not wire the Profile controller or change the visible Profile layout before that gate. Its internal FeedViewport contract exposes `emptyPosition: FeedPosition`, `position(): FeedPosition`, `readingOlder(): Boolean`, `nearEnd(rowCount:Int): Boolean`, `restore(position:FeedPosition)` and `revealFirstStatus()`. Generic pager code keeps snapshot identity recovery and normalization inside the cache/lifecycle boundary. The ordinary list adapter may retain its old leading-content path only until the subsequent Profile integration removes that last caller. Profile's future adapter must keep cached footer positions safe independently of its reading-older decision. The status lifecycle is extracted once as internal `rememberStatusPager(ui,source,viewport,isActive)` and reused by existing feeds before Profile adopts it. Notification grouping behavior stays unchanged. This is a staged caller migration, not a second lasting Profile renderer.

## Gates and acceptance

Read the pinned Compose 1.12.2 APIs before relying on new motion behavior. The prototype must establish empty-body header travel and native interaction before live feed wiring. Verify parent-origin fling into posts, reverse motion, pull-to-refresh ordering, accessibility scrolling and bring-into-view, clipping, and large text. Unsupported or inconclusive behavior is not a pass. Resolve failures at the owning controller; repeated structural workarounds return to architecture comparison.

Final integration must pass the three original native failures and all five category transitions, Activity filters, short/empty/loading states, source cancellation, actual clipped pagination, header/status return from Accounts, legacy leading/status snapshots, deleted anchors, rapid A/B/A switches and delayed writes. Verify all seven Settings children, index/caller back, Accounts return, guests, locale and dirty composer behavior. Reuse prior Home source-retention and visual-polish cases. Build Android Release and signed iOS Release 0.6.5 build 11, install in place on the authorized physical iPhone, and read back version/startup. No live post or photo-library writes are required.

Root accepts this synthesis from the current user request, documented baseline failures and independent cross-judge verdict. Accepted deviations must update this artifact before the next unit consumes a changed contract.
